DeepSeek Harness 的《Super-agent 设计探索》提出：限制 Agent 生产力进一步提升的瓶颈，正在从"模型能不能做"转向"人能不能盯"。本文将这一判断放回公开研究的坐标系中，梳理过去三年 Agent 系统各层的工作、已收敛的结论与仍属空白的问题，并正面处理与之相悖的证据。

# 1 范围与组织方式

关于 Agent 的文章数量庞大，但绝大多数讨论的是同一问题：如何让模型在单个回合内做得更好——提示词怎么写、工具怎么描述、推理链怎么组织、上下文怎么装载。

Super-agent 讨论的是另一问题：当几十个任务同时进行、事件从多个来源涌入、而人只有一份注意力时，系统应如何组织。

这一问题在传统计算机系统中有大量先例——调度、缓存、隔离、持久化、控制回路。因此本文不按时间线罗列，而按系统层次组织：将 Agent 系统拆为五层，观察每一层的公开工作沉淀了什么、留下了什么。

# 2 五层抽象

本文的分析框架将 Agent 系统自下而上分为五层：

![](/assets/article-images/super-agent-stack.png)

- **L0 运行时与执行环境**：进程、状态、机器、故障——系统能否持续运行。
- **L1 控制循环**：模型在单个回合内如何推理、动作、观察。
- **L2 上下文与记忆**：窗口内放什么、窗口外留什么、如何再找回。
- **L3 编排与会话组织**：谁来决定"此事交给谁"，并发如何成立。
- **L4 组织与协议**：实例之间、实例与人之间的边界与握手。

一个粗略但有解释力的观察是：L1 与 L2 是学术工作最密集的层次，L3 与 L0 主要由工程实践推动——后两层的问题仍停留在"各有各的做法"阶段，尚未收敛出公认的抽象。

# 3 L1 控制循环：已基本收敛

**ReAct**（[arXiv:2210.03629](https://arxiv.org/abs/2210.03629)，ICLR 2023）确立的范式至今未被替代：在同一条轨迹中交替产生推理步骤与动作，使模型边想边做、边做边看。其贡献不止于效果，而在于给出了最小完整形态——观察（observation）回灌进上下文，构成"上下文增量写入"的基本单位。当前所有 Agent 框架，内核均为这一循环。

**Reflexion**（[arXiv:2303.11366](https://arxiv.org/abs/2303.11366)）在循环之外增加一层：任务失败后，以语言反馈生成"反思"，存入情节记忆，下次同类任务时召回。它不更新权重，只更新记忆。

**SWE-agent**（[arXiv:2405.15793](https://arxiv.org/abs/2405.15793)，NeurIPS 2024）的贡献在于将 **ACI（Agent-Computer Interface）** 作为一等设计对象：文件查看、编辑、搜索均有专门接口，使模型不易犯错——相比之下，"给模型一个 bash"是最省事、也最容易出错的方案。这是"环境设计比提示词更重要"的早期证据。

这一层的收敛程度很高：几乎所有严肃的 Agent 系统都在使用 ReAct 式循环，差别仅在工具设计、上下文组织与停止条件；真正的分歧发生于 L1 之上。

该文在这一层仅做一处改动，但改动关键：将同步的 `run()` 拆为异步的 `start()` / `stop()`，使循环不被工具阻塞。其本质是将会话从半双工变为全双工，属"以系统手段解决交互问题"。

# 4 L2 上下文与记忆：从"更大的窗口"到"更少的 token"

这一层的工作最多，也最易走弯路；弯路的名字是"窗口够大就行"。

## 4.1 三次概念跃迁

**第一次跃迁：把上下文当作操作系统资源。** **MemGPT**（[arXiv:2310.08560](https://arxiv.org/abs/2310.08560)）提出 "virtual context management"：将上下文窗口类比为 OS 内存分层，模型通过函数调用在快慢存储之间换页，以中断管理控制流。这是"上下文是稀缺资源"说法的源头。

**第二次跃迁：把记忆分类。** **CoALA**（[arXiv:2309.02427](https://arxiv.org/abs/2309.02427)，TMLR 2024）给出至今最常用的词汇表：工作记忆与长期记忆（情节 / 语义 / 程序），动作分内部与外部，决策为规划与执行的交替。

**第三次跃迁：把检索变成打分。** **Generative Agents**（[arXiv:2304.03442](https://arxiv.org/abs/2304.03442)，UIST '23）的 memory stream 是链式召回的原始范式：观察按时间写入流，检索时按相关性、新近性、重要性加权取回，再由 reflection 合成高层推断写回。其消融实验指出，最常见的失败在检索环节——记忆并未丢失，但检索不到相关的那条。

该方向另有两条分支：**Voyager**（[arXiv:2305.16291](https://arxiv.org/abs/2305.16291)）将技能固化为可执行代码库，即程序性记忆；**Mem0**（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)）将记忆做成"抽取 → 归并 → 检索"的生产级管线。

## 4.2 反面证据

**Lost in the Middle**（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)，TACL 2023）表明，相关信息位于长上下文中部时，性能显著下降，呈 U 形曲线，且长窗口模型同样如此——"塞进去"与"用得上"是两回事。

**Context Rot**（[Chroma，2025-07-14](https://www.trychroma.com/research/context-rot)）将其进一步实证：18 个模型、控制任务难度只改变输入长度，全部出现退化且退化不均匀；在 LongMemEval 上，聚焦输入（约 300 token）显著优于完整输入（约 113k token）；甚至单个干扰项即造成下降。

两篇反面证据与 MemGPT 并读，可得出一致的结论：上下文管理的目标是在正确的时刻装载正确的少量，而非装载更多。

## 4.3 工程侧的三手段

Anthropic 的 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（2025）将这一思路落为三个手段：

1. **Compaction**：接近窗口上限时摘要后重启窗口，保留架构决策与未解缺陷，丢弃冗余工具输出。
2. **Structured note-taking**：将关键状态写入外部笔记，跨窗口重置续接。
3. **Sub-agent**：以干净窗口深挖子问题，仅回传 1–2k token 的结论。

三种手段与该文的 Inline & Spill 是同一方向的不同表述：把窗口当 Cache，按局部性决定内容的进出。

但二者存在一个重要差别，也是该文的一处空白：Anthropic 的三手段包含写回与压缩（compaction 产生新摘要、note-taking 落盘），而 Inline & Spill 主要描述读入。该文的链式召回解决了"如何找回"，但未回答"何时写回、版本冲突如何消解、旧信息何时遗忘"。

# 5 L3 编排：并行与否的正面冲突

这一层不存在渐进积累，只有一场公开的路线之争。

## 5.1 支持方：并行换取探索宽度

Anthropic 的 [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)（2025-06）给出三组数据：

- 多智能体系统消耗的 token 约为聊天的 **15 倍**（单 Agent 约 4 倍）；
- Opus 4 主导 + Sonnet 4 子 Agent，比单用 Opus 4 高 **90.2%**；
- 在 BrowseComp 上，**token 用量一项解释了 80% 的方差**。

第三项最关键：多智能体的收益很大程度上来自投入更多算力并行探索，而非"协作更聪明"。该文同时记录了代价：子 Agent 同步执行形成信息流瓶颈——"lead agent 无法指挥子 Agent，子 Agent 之间无法协调，整个系统可能卡在等待单个子 Agent 上"。其附录提及让子 Agent 产物直接写文件系统、绕过主协调器，以避开"传话游戏"。

## 5.2 反对方：共享上下文比并行更重要

Cognition 的 [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)（2025-06-12）提出两条原则：

1. **Share context**：共享应共享完整轨迹，而非单条消息。
2. **Actions carry implicit decisions**：每个动作携带隐含决策，互不知情的 Agent 各自决策，冲突是必然的。

其结论是：默认排除不满足这两条的架构，最可靠的方案是单线程线性 Agent；上下文溢出交由专职压缩模型处理。

需要澄清的是，Cognition 反对的是"决策分散 + 上下文不共享"，并行本身并不在反对之列——其对"只回答问题、不写代码、不与主 Agent 并行"的 subagent 仍予认可。

## 5.3 工程侧的折中

将这场争论视为"谁对"，会忽略更有价值的部分：工程界已在用具体机制调和二者。

**AutoGen v0.4** 是最强的先例。其 core 层重写为 actor 模型，投递分直投与广播，广播以 pub/sub 实现：`Topic = (Topic Type, Topic Source)`，`TypeSubscription` 将类型映射到 Agent 类型，而 Agent ID 的 key 直接取 topic source，实例不存在则惰性创建。文档中 "in event-driven workflows, agents do not always know who will handle their messages" 一句，几乎是对"订阅直通"的直接描述。

将 AutoGen 的机制与该文的 3.2 节并排，可见该问题已被解决过一遍：

- 「同一 PR / 话题 / 邮件串构成 Thread」→ topic source 以 thread 标识；
- 「Worker 订阅 Thread」→ type subscription 将 topic type 映射到 Agent 类型；
- 「首事件创建 Worker、后续直通」→ 实例不存在时惰性创建；
- 「直通绕过 Router、不经中心逐个判断」→ 路由规则声明一次，broker 退化为连接与注册。

**Magentic-One**（[arXiv:2411.04468](https://arxiv.org/abs/2411.04468)）提供另一可复用机制：外环维护 task ledger（已知 / 待查 / 待推 + 分步计划），内环每轮生成 progress ledger 回答五个问题（是否完成、是否原地打转、是否还有进展、下一个该谁、该问什么），并带 stall counter，超过阈值即跳出内层重新规划。这一 stall counter 与该文的 Watchdog 是同一机制的两种形态：以廉价信号判断"是否还有实质进展"。区别在于 Magentic-One 将其置于循环内，该文置于主系统之外。

**MetaGPT**（[arXiv:2308.00352](https://arxiv.org/abs/2308.00352)）则代表另一极端：将 SOP 编码为 prompt 序列，角色流水线写死，相当于 100% 确定性 Fast Path、零动态路由。它在流程稳定的领域有效，其分界在于任务的可预测性。

## 5.4 四种编排范式

- **固定 SOP（MetaGPT）** —— 路由由代码写死，上下文按角色持有，适合流程稳定的任务。
- **对话式（早期 AutoGen）** —— 路由由模型临场决定，上下文为共享对话历史，适合探索性任务。
- **中心编排（Anthropic orchestrator-worker、Magentic-One）** —— 主 Agent 规划分派，子 Agent 隔离上下文、只回传结论，适合可并行拆分的宽任务。
- **单线程线性（Cognition）** —— 无路由，全程单一轨迹，适合强耦合、隐含决策密集的任务。

该文的双层架构不属于上述任何一类：它将"路由"与"执行"分至两层，路由只做任务间归属，执行完全隔离。以此对照，其独特性在于假设任务之间弱耦合——该假设在研发协作场景成立（不同 PR 相对独立），在强耦合场景则退化。

# 6 L0 运行时：状态应当置于何处

这一层是纯工程，却是"能否持续在线"的物理基础。四条主流路线：

- **事件历史重放（Temporal）**：工作流代码从头重放事件历史，内存不从快照恢复；因此代码必须确定性——"给定相同历史必须做出相同决策"。LLM 调用置于 Activity，仅执行一次，重放时复用结果。其哲学是：状态可推导，无需单独保存。
- **检查点（LangGraph）**：以 super-step 为单位做 checkpoint，加上节点级 pending writes；`thread_id` 为主键。其哲学是：状态是快照，可回滚至任一步。
- **有状态对象（Cloudflare Durable Objects）**：每个 Agent 即一个 Durable Object，状态绑定对象，空闲后驱逐，恢复靠同步落盘。其哲学是：状态与身份绑定，对象在哪状态在哪。
- **无状态 harness + 外部会话日志（Anthropic）**：最激进的一种。Anthropic 在 [Scaling Managed Agents](https://www.anthropic.com/research/managed-agents)（2026）中将系统拆为三个接口：brain（模型 + harness）、hands（沙箱与工具）、session（事件日志）：

> The solution we arrived at was to decouple what we thought of as the "brain" (Claude and its harness) from both the "hands" (sandboxes and tools that perform actions) and the "session" (the log of session events). Each became an interface that made few assumptions about the others, and each could fail or be replaced independently.

harness 因此"离开容器"，成为可随意重启的 cattle：崩溃后以 `wake(sessionId)` 重建，以 `getSession(id)` 取回事件日志，从最后事件继续。代价是延迟，收益是 p50 TTFT 下降约 60%、p95 下降超过 90%。

四条路线的对照可以压缩为一条标准：崩溃之后，系统需要重算多少东西。事件重放靠确定性重算，检查点靠回滚，有状态对象靠落盘续命，无状态 harness 将状态推到系统之外、靠读日志重建。

该文的 5.1 节属于第四条路线的简化版（计算入云、状态入库），但未走到"harness 可抛弃"一步——其 Router 是常驻 Session，尚不能像 cattle 那样随时重启。

## 6.1 执行环境：为何不应"搬到云上"

第二层解耦拒绝了两条常见路径：云端重建环境（复制不全）、用户迁移上云（成本过高）。

公开资料对此有明确支持。**Factory** 的 [Droid Computers](https://factory.com/news/droid-computers)（2026-04）将其命名为 **BYOM（Bring Your Own Machine）**：可远程控制运行于笔记本或工作站上的 Droid，且 BYOM 机器向外连接后端，无需额外网络配置。**E2B**（[沙箱持久化](https://docs.e2b.dev/sandbox/persistence)）与 **Modal**（[VM Sandboxes](https://modal.com/blog/vm-sandboxes-agent-computers)，2026-10）提供另一侧答案：环境可为云端、可暂停恢复、甚至是一台完整 VM。

因此真实图景中不存在"端侧 vs 云端"的对立：执行环境成为一种可插拔的资源——用户设备、云 VM、按需沙箱，均经统一接口接入。该文的"轻量 daemon"是其中一种实现。

# 7 L4 协议：三条边界

三个协议分管三件不同的事：

- **MCP（Agent → 工具 / 数据）**：server 暴露能力，client 接入，替代 N×M 的自定义连接器，属纵向集成。
- **A2A（Agent ↔ Agent）**：以 Agent Card 发现能力，以 Task 状态机与 SSE 流推进协作，属横向对等。
- **AG-UI（Agent → 人）**：以事件流描述 Run / Step / Text / ToolCall / State / Subagent 的全部进展，属前端交互。

MCP（[Anthropic，2024-11](https://www.anthropic.com/news/model-context-protocol)）解决 N×M 的集成爆炸；2025-06-18 修订加入 **elicitation**——server 可在中途反向向用户索取信息，将"Agent 主动向人发起事件"写入协议层。

A2A（[规范](https://a2a-protocol.org/latest/)）的设计原则之一是 **Opaque Execution**：不暴露内部 memory 与 tools。该原则恰好回应该文 8.3 节的困惑——A2A 管的是实例之间，而"共享 Thread 广播"发生在实例内部，二者对上下文可见性的要求正好相反，分属不同层次。

AG-UI 的事件设计对交互层有参考价值：`StateDelta` + `MessagesSnapshot` 是"增量广播 + 快照补齐"的现成范式，`Subagent*` 事件表明多个 Worker 的存在可对外观察，这补上了该文 8.2 节"Session 隐藏后用户如何感知任务"的一半答案。

# 8 反面证据

综述最易犯的错，是只收集支持论点的材料。本节专门处理相反的证据。

## 8.1 可靠性：pass@1 是虚假指标

**τ-bench**（[arXiv:2406.12045](https://arxiv.org/abs/2406.12045)）提出 `pass^k`：k 次运行全部成功的概率。gpt-4o 在 τ-retail 上 pass^1 约 61%，pass^8 低至约 25%——同一个任务连续八次全对的概率只有四分之一。对每天运行数百次任务的系统，用户体验由 pass^k 而非 pass@1 决定。

## 8.2 失效模式：问题出在验证层

**MAST**（[arXiv:2503.13657](https://arxiv.org/abs/2503.13657)，NeurIPS 2025）分析 1600 余条轨迹、7 个框架，归纳出 14 种失效模式、3 大类：系统设计、智能体间错位、任务验证。

第三类最关键：缺乏独立验证层时，错误只会被传递而不会被发现。这直接支持 Watchdog 的设计，但亦提示 Watchdog 需要真正的验证能力（可执行检查、外部信号、人的判断），而非"再跑一个 Agent 看看"。

## 8.3 成本：复杂编排未必更优

**AI Agents That Matter**（[arXiv:2407.01502](https://arxiv.org/abs/2407.01502)）做两件事：其一，证明准确率相近时成本可差近两个数量级；其二，给出三个极简基线（retry / warming / escalation），其在 HumanEval 上不显著劣于当时的 SOTA 复杂 Agent。

后者是对所有架构论文的通用质疑：是否跑过更简单的基线。该文以"单 Session + Subagent"这一简单基线做对照，在此意义上合格；但未做成本折算（见《Super-agent 架构精读》第 6.3 节）。

## 8.4 能力趋势：窗口正被模型自身侵蚀

**METR** 的 [Measuring AI Ability to Complete Long Tasks](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)（2025-03，arXiv:2503.14499）给出结论：50% 可靠度的任务时长约每 7 个月翻倍。

该数字需附带三个限定：这是 2025-03 的口径（该页已标注部分内容过时）；METR 亦注明超过 16 小时的测量不可靠；且 SWE-bench Verified 子集的翻倍周期更短。

即便如此，其含义明确：若模型每 7 个月即可独立完成更长的任务，"以架构补模型"的红利窗口将不断收窄。依赖"模型做不好长任务所以需要拆分"的架构，需在模型增强后重新论证。

## 8.5 人的一侧：监督成本上升

Anthropic 的 [Measuring AI agent autonomy in practice](https://www.anthropic.com/research/measuring-agent-autonomy) 给出与直觉相反的数据：Claude Code 的中位单轮时长仅 45 秒，而 99.9 分位在三个月内从不足 25 分钟升至超过 45 分钟；用户打断率同期从 5% 升至 9%。复杂任务上仅 67% 有某种人工参与（简单任务为 87%），报告据此提出 "deployment overhang"——能力已超过实际部署中允许的自主度。

这对"人的注意力是瓶颈"既是加强，也是质疑：若监督成本随自主度上升，"减少打扰"与"提高可靠性"可能是一枚硬币的两面，而非两个独立目标。

# 9 《Super-agent 设计探索》在谱系中的位置

综合上述六层，可对《Super-agent 设计探索》作一准确定位。

## 9.1 三项贡献

- **将 Session 从产品概念降级为实现细节。** 一旦 Session 不再是用户单位，上下文归属必须由系统显式管理，这直接导出 Router / Worker 的分层。
- **将 Fast / Slow Path 贯穿全系统。** 过滤、路由、上下文组装、投机执行共用同一套"确定性代码 + 模型兜底"，新增信道或事件类型只需改配置与提示词。
- **将执行环境留在原地。** 与 Anthropic 的"脑手分离"方向一致但场景不同（个人设备 vs 托管沙箱），因此在信任模型上留有更大空间（文章 8.4 节自认）。

## 9.2 三处空白

- **写回与遗忘。** Inline & Spill 主要描述读入；记忆的写入策略、版本冲突、遗忘机制，文章未展开，公开工作中亦无可复现的评测。
- **长程记忆的入口。** 链式召回假设"仍记得入口"；跨月之后，人自身已不记得任务对应的 Thread，系统亦无从主动提示。
- **监督成本未被建模。** 设计的隐含承诺是"人仅在决策与验收时介入"，但 8.5 节数据表明介入是分钟级且随复杂度上升。若一次验收需人读三分钟，并发十个任务即超出人的带宽，"减少打扰"反而制造验收队列。

# 10 最小可行的 Super-agent

将上述材料压缩为一份执行清单，顺序即依赖关系：

1. **先做对事件入口。** 不急于多 Agent。先做 Fast / Slow 两级过滤与事件级幂等。Hookdeck 的判断是：多数"Agent 工作流"的真实故障只是投递与重试问题（LLM 超时、进程重启、下游抖动），ack-then-process 即可解决大半。
2. **将会话状态外置。** 即使只有一个会话，也先将日志写到 harness 之外，方能在后续将计算变为无状态。
3. **增加只做分派的 Router。** 其约束是不配备执行工具；这一约束使连续性获得稳定归属。
4. **增加订阅直通。** 以 Thread ID 为 key 即可；其收益在压测中显现，且是 Router 不被压垮的前提。
5. **最后增加 Watchdog。** 置于主系统之外，检查"Worker 最近是否有实质进展"，进程存活只是底线。

五步的共同逻辑是：每一步都在缩小"必须由人兜底"的面积。

# 11 结论：架构购买的是验证成本

这套架构是否成立？答案是：它在"长时程、多任务、事件密集"的交集内成立，且成立的理由在于其能更便宜地验证，而非更聪明。

支持面的证据充分：pass^8 的崩塌说明单次成功率意义有限；MAST 的第三类失效说明错误必须被独立发现；Anthropic 的自主性数据说明人的介入是分钟级且随复杂度上升。

反面证据同样充分：METR 的翻倍曲线持续侵蚀"架构补模型"的窗口；AI Agents That Matter 提醒复杂编排常不优于三个极简基线；Context Rot 说明"塞进窗口"本身在退化。

综合两侧，最稳妥的表述是：

> 在当前的能力水平上，架构是绑定约束（binding constraint）；其价值来自压低验证与注意力的成本，系统复杂度本身不产生价值。一旦模型的可靠任务时长跨过某个阈值，该架构的多数部件将退化为可选优化，而"验证"这一层会保留。

这亦解释了 Watchdog 一节的被低估：整套设计中，它是唯一直接面对"如何确认结果可信"这一问题的部件。
