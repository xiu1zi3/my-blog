DeepSeek Harness 团队于 2026 年 10 月底发布的《Super-agent 设计探索：迈向更自主的 Agent 系统》，将"Agent 应当具备何种形态"这一问题，从产品交互层面重新放回系统架构层面。本文对该文逐节解析，并给出三点需要审慎对待之处。

# 核心结论

文章的核心判断如下：

> 在这种设计下，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

过去两年 Agent 能力的提升集中在"单任务上限"一侧：ReAct 使模型能够使用工具，Coding Agent 使模型能够修改代码，长上下文使模型能够容纳整个仓库。而另一侧的上限几乎未动：一个人能同时跟进多少个活跃任务？

作者的观察是 **3 到 5 个**。当 Agent 以单个 Session 为基本单位、且 Session 之间彼此独立时，并行推进多项工作意味着在多个窗口之间手动切换，并自行维护"哪份上下文在哪"。无论模型如何增强，吞吐都受制于人的工作记忆。文章的全部设计，都在解除这一约束。

## Session 应是实现细节

文章给出的题眼是：

> Session 应当是系统的实现细节，而不应是用户的认知负担。

当前 Agent 产品普遍将 Session 暴露给用户：一个任务对应一个对话，切换任务即切换对话，上下文丢失即新建对话重新陈述背景。这一形态沿袭自底层 LLM API 的 `messages` 数组——API 以"一次请求携带一段消息历史"为单位，产品便以"一个会话"为单位。

Super-agent 的方案，是放弃"把 Session 做得更好用"，转而将其隐藏：用户面对的始终是同一个 Agent，底层的会话数量、生命周期与合并策略均由系统接管。

# 单会话的局限

文章将"在本地单会话 Agent 上挂载 CLI、MCP 或外部连接器"这一路径的限制归纳为三条，本文补充第四条：

- **同步阻塞** —— 工具调用执行期间，会话无法响应新输入。根因是 ReAct 循环本身是同步的 `run()`。
- **上下文混杂** —— 多个任务的中间细节堆叠于同一窗口，相互污染。根因是一个 Session 对应一份上下文。
- **离线即停** —— 设备休眠或离线后，Agent 即停止运行。根因是计算、状态、环境绑定于同一台设备。
- **交互错位** —— 面向单人的推理过程原样输出至群聊，造成信息过载。根因是输出未按信道定制。

前三条是能力问题，第四条是体验问题。文章将第四条同样视为架构问题（见"面向人的交互"一节），而非提示词问题。

# 四个特征与五个模块

文章先给出 Super-agent 的四项定义，再说明单个 ReAct Loop 无法同时满足这四项，据此导出五个模块：

- **连续** —— 用户跨 IM、GitHub 等界面交互，始终面对同一个 Agent。架构上要求全局上下文具有稳定的归属。对应**双层架构（Router 层）**。
- **高效** —— 后台执行长任务的同时，前台仍可接受新指令。架构上要求并发执行与前台响应互不阻塞。对应**双层架构（Worker 层）+ 异步 ReAct**。
- **主动** —— 无需逐条指令，持续观察环境事件并自主推进。架构上要求输入从提示词转为环境事件。对应**事件驱动（过滤 / 路由 / 投机执行）**。
- **持久** —— 跨设备、断网、崩溃后仍持续运行。架构上要求计算、状态、环境三者解耦并具备自愈能力。对应**存算分离 + Watchdog**。

这四项特征两两成对：连续与高效是一对矛盾（串行与并行的张力），由分层化解；主动与持久是另一对风险（越主动越易接触不可信输入与异常），由事件驱动与外部看门狗兜底。

# 双层架构

## 连续性与吞吐量

文章开篇即指出：所有事件交给同一个 Session，上下文最连续，但吞吐受单循环速度约束；每条事件新开 Session，吞吐最高，但上下文割裂、多个会话各自回复造成混乱。

"两种方案各有优劣"的表述并不构成分析；二者之间的取舍是一条真实的边界——沿着边界移动，只是在连续性换取吞吐。

![](/assets/article-images/super-agent-tradeoff.png)

Super-agent 并不在边界上寻找最优点，而是换一个维度：将"维护连续性"与"执行任务"分配给两个层级。Router 层负责承接人类交互、维护全局上下文；Worker 层在隔离的上下文中执行具体任务。连续性只在一个常驻会话内维护，因此不再随并发数线性退化。分层之后，多任务的上限从人的注意力回到系统吞吐。

## Router 层

Router 层最易被误读为 Agent Team 的 Team Lead。二者的区别在于分工粒度：

- **分工粒度**：Agent Team 拆解单个复杂任务内部的步骤；Router 分派多个任务之间的归属。
- **推理负载**：Team Lead 需理解细节、规划子任务并高频协调；Router 仅判断"此事归谁"。
- **执行能力**：Team Lead 常亲自执行；Router 无需执行工具，甚至可以不配备 Bash。
- **失败模式**：Team Lead 易被细节拖累；Router 可能分派错误，但可分派重试。

"不装 Bash"这一约束的意义在于，全局节点最易成为瓶颈，而最易使其变慢的，是让它执行具体工作。文章指出，Router 常以轻量模型即可胜任。

那么单个常驻 Session 为何未成为吞吐瓶颈？答案是**批处理**：上一轮推理期间到达的事件积压至下一轮一并注入。Router 每步为"长输入、短输出"，多条 Trigger 合并进一次调用时，Prefill 阶段并行计算，单次请求耗时的增长远慢于 batch 的增长。"实验结果"一节将给出量化结果。

## Worker 层

Worker 层由上下文彼此隔离的执行会话组成，挂载完整工具，专注完成单一任务，通常配置能力最强的模型。

其硬约束是**不直接与人类交互**：推理过程与工具调用不外泄，仅向 Router 汇报状态，由 Router 统一回复。这一约束解决了多会话各自回复的混乱，同时将"输出风格"从执行层剥离——执行层对正确性负责，表达层对信道负责。

Worker 之间不点对点通信。多个 Worker 在同一 Pull Request 等共享环境中产生冲突时，只要它们订阅了对应 Thread，便会收到相同的事件通知，从而自行发现并消解冲突。

# 事件驱动

第 5 节描述"事件从进入到被处理"的完整生命周期。其核心洞见是：同一个设计母题被复用了四次——**Fast Path / Slow Path**，即把确定性的、高频的判断固化为代码，只把需要语义理解的少数情况交给模型。

![](/assets/article-images/super-agent-event-flow.png)

- **过滤**：真实群聊呈"高噪音、低触发率"特征。程序层先按来源、群组、白名单做准入检查，只将候选事件交给模型；语义层同时作为自然语言策略的扩展点。
- **路由**：已归属的后续事件由程序直接投递给订阅了对应 Thread 的 Worker；Router 只处理尚未被订阅的新事件，避免成为所有事件的转发瓶颈。
- **上下文组装**：注入过多挤占窗口、稀释注意力，注入过少迫使模型反复调用工具。文章将这一权衡抽象为 **Inline**（近期大概率用到的信息直接内联）与 **Spill**（超出预算的信息留在窗口外，仅保留引用）。
- **投机执行**：在结果是否会被采用尚不确定时，先在后台尝试。文中实例为：用户群内有人反馈问题，Agent 先在后台复现并寻找修复方案，确认后才交付，否则保持静默。

## Thread 与订阅直通

路由成立的前提是事件具有天然的归属结构。同一个 Pull Request、IM 话题或往来邮件串下的连续事件，构成一条 **Thread**。

Thread 与 Worker 的订阅关系是多对多的：一个 Worker 可订阅多个 Thread，一个 Thread 可被多个 Worker 订阅。这一设计同时解决了两个问题——共享环境中并发 Worker 的冲突（广播使彼此可见），以及少数跨任务协同（由 Router 中转）。

# 上下文组织

## Inline、Spill 与链式召回

文章借用编译优化的概念，将上下文注入归纳为三步：

1. **从最少信息开始**：仅提供当前对象的 ID 与摘要。
2. **按局部性逐步 Inline**：先附带紧密关联对象的 ID，再附带时空相邻的内容。
3. **超上限则 Spill**：截断并保留续读入口，需要完整内容时再调用工具。

将同一规则一致地应用到所有对象后，形成**链式召回**：系统为 Trigger、Thread、Worker Session 分配唯一 ID，注入时内联下一跳对象的 ID，使这些对象在底层构成一张引用图。模型从当前事件出发，可沿引用关系逐跳展开上下文。

![](/assets/article-images/super-agent-recall.png)

这解释了 Router 层为何能在不将全部历史塞入窗口的前提下，仍能在用户提及旧任务时召回上下文：它无需记住全部内容，只需记住入口。

## 实验结果

第 7 节给出两组数据。第一组为端到端消融：约 300 条消息（其中约 20 条为工作请求）、4 种方案、各运行 5 次；编码工作以只耗时工具替代，以衡量调度与协作能力。

![](/assets/article-images/super-agent-metrics.png)

- Super-agent 的 p50 / p95 为 **12.4 / 15.7 分钟**，显著优于"单 Session + Subagent 工具"。
- 中性提示下，模型 5 次运行**均未调用 Subagent**，全部工作在主会话内进行并不断被打断，p95 达 29.5 分钟。
- 改为"提示优先委派"后，5 次中有 4 次委派，但仍有 1 次模型判断工作过小而自行执行，形成长尾。

这组数据的价值在于揭示了提示词工程在并发场景下的不可靠：无法以一句 prompt 保证模型每次都做出正确的分工决策，因为分工与否取决于模型的临场判断，系统并未在结构上约束它。双层架构将这一约束落为结构——Router 在物理上不配备执行工具，Worker 在物理上只接收其订阅的消息。

![](/assets/article-images/super-agent-batching.png)

第二组为 Router 层的压力测试。Trigger 到达速率从每分钟约 1 条升至 40 条时，平均 batch 从 1.0 升至 2.8，单次请求耗时仅从 2.5 秒增至 3.9 秒，增长慢于 batch，单个决定分摊的推理时间因此从 6.4 秒降至 1.6 秒。拥堵非但未使 Router 失效，反而提高了其有效吞吐；这也解释了为何 7.1 节中去除直通、Router 峰值负载增加 30% 后，系统仍未触及吞吐瓶颈。

代价是 token 开销：去除直通后，总读缓存 token 从 2323 万增至 3177 万（+37%）。作者的结论是：直通不提升完成质量，但为 Router 节省了可观的推理开销。

## 三点保留意见

实验设计与结论存在三处值得注意的边界：

**其一，样本量。** 单次实验仅约 20 个工作请求，5 次运行合计约 100 个样本。在这一规模下，p95 只是"最大值附近的一两个点"，其统计效力有限。作者亦自述"部分设置还可以更加严谨"。

**其二，任务替换。** 编码工作被替换为只耗时工具，实验衡量的是调度与协作，而非执行能力。若真实任务的耗时分布为重尾分布，批处理与直通的收益结构可能随之改变。

**其三，成本未折算。** 多会话意味着更多的 prefill，而 prefill 同时影响费用与首字延迟。文章给出了 token 量，但未给出单位任务的成本对比——这是决定是否采用该架构的关键指标。

上述保留不影响整体结论。相反，一篇将"合成负载、结果仅供参考"写入正文的工程文章，其可信度高于仅呈现理想曲线的文章。

# 面向人的交互

第 4 节容易被当作性能优化章节，但其讨论的是交互语义。

## 全双工

经典 ReAct 循环中，模型发起一次同步的 `run()` 调用后，循环阻塞直至工具返回，期间无法响应任何新输入。

改造方案是将耗时命令与子任务调用替换为异步的 `start()` / `stop()`：`start()` 后立即收到 "Started"，循环继续；后台执行完成后，结果作为一条新事件投递回会话；模型可调用 `stop()` 主动终止执行过长的后台命令。

这一改动使会话从半双工变为全双工，前台对话与后台执行解耦，新输入在当前推理步结束后即可被处理。文中注明，该机制"已经在 DeepSeek Harness 中实现，但尚未默认开启"——这提示异步化牵动的是整个执行模型，而非单处代码。

## 多信道

不同信道具有不同的信息密度与交互习惯。面向单人的推理过程原样输出至群聊，即造成信息过载。

文章给出的两个原则是：IM 等即时信道，单次回复不超过 100 词；GitHub、邮件、文档等异步信道，交付结构化、高信息密度的内容（问题背景、改动说明、验证结果）。"100 词"是写进提示词的硬性规定，而非交由模型自觉——这再次印证了全文的方法论：能固化为规则的，不依赖临场判断。

# 持久与自愈

第 5、6 节处理"Agent 是否会终止"的问题，其两步解耦思路源自分布式系统。

## 两层解耦

本地 Agent 将三类资源绑定于一台设备：推进循环的计算、需要持久化的会话状态、以及代码仓库与工具链等执行环境。设备休眠，三者同时停止。

- **第一层：计算与状态分离。** 计算置于云端无状态容器（可水平扩缩、可重启替换），状态入库，成为连续性的唯一真相来源。
- **第二层：计算与执行环境分离。** 环境不上云，留在原地，端侧仅部署不保存状态的轻量 daemon，负责执行命令与返回结果。

第二层的争议与价值并存。常见的替代方案有两类：云端起沙箱、拉取代码并重建环境（真实环境中的未提交修改、私有凭据、内网依赖、特定硬件难以复制）；或要求用户迁往云端（迁移成本过高）。作者的判断是：既然难以复制的是环境本身，就不必让环境跟随循环上云。

该设计支持 **BYOM（Bring Your Own Machine）**——将日常开发机接入云端 Agent；亦支持云端托管机或按需沙箱，并可处理间歇在线的设备。

## 与"脑手分离"比较

文章指出，这一思路与 Anthropic 的"脑手分离（Decoupling the brain from the hands）"一致：harness 保持无状态，会话日志存于 harness 之外，通过统一接口按需接入执行环境。

差异在于场景：Anthropic 描述的是托管服务（按需创建的沙箱与客户 VPC 内的资源），而 Super-agent 首先要接入的是用户日常使用、可能间歇在线的个人设备，其上存有未提交的修改与本地凭据。这一差异决定了二者在信任模型上的不同，文章在第 8.4 节对此亦有承认。

## Watchdog

持久在线的第二个前提是异常自愈。文章观察到：

> 许多异常并非进程崩溃，而是模型在执行中陷入无效循环或偏离目标。

因此传统的存活探测并不充分。方案是在主系统之外放置一个独立的 Watchdog Session，以定时消息驱动，构成外部控制回路：既处理接口报错、状态恢复失败等基础设施故障，也由模型判断各 Worker 是否取得实质进展、方向是否偏离目标。

将其置于主系统之外是关键——一个已经跑偏的系统无法自行发现偏离。由于 Watchdog 本身即具备完整工具能力的 Agent Session，维护者可用自然语言查询故障原因，或令其在线修正主系统的行为（增删提示词、调整触发规则）。

# 三个隐含前提

该架构的适用范围依赖三条隐含前提：

- **Router 的任务足够简单。** "轻量模型即可胜任"的判断源于实践，但依赖任务之间关联较浅。若任务高度耦合、需要频繁互相引用上下文，Router 的判断成本将上升，"不装 Bash"亦可能不再充分。
- **团队规模有限。** 单个常驻 Router Session 在"当前团队规模"下够用。规模扩大后需多层过滤或水平切分，而切分将牺牲跨分片的记忆连续性——在全局记忆问题解决之前，这一权衡持续存在。
- **环境彼此可信。** 云端循环加端侧 daemon 的架构，默认云端与端侧互信。一旦云端被提示词注入攻破，其连接的全部端侧设备均面临被控制的风险；即便云端未被攻破，凭据一旦进入模型上下文亦有泄露风险。

# 开放问题

文章末尾列出四个开放问题，其重要性与成熟度并不相同。

**双层架构如何扩展（8.1）。** 两个子问题：Router 何时需要水平切分、Worker 之间何时需要直接通信；以及长程记忆——链式召回解决的是近期任务与会话历史的按需检索，当运行周期拉长至跨月，长程记忆成为主要瓶颈。链式召回本质上是"按引用图导航"，其前提是仍记得入口；跨月之后，人自身已不记得三个月前任务对应的 Thread，系统亦无从召回。

**脱离 Session 后的协作形态（8.2）。** Session 隐藏之后，"项目管理"成为独立的产品问题。文章认为以聊天窗口为中心的交互是路径依赖，交互可以更多发生在领域特化的界面中，例如直接在 GitHub 的 Issue 与 Pull Request 中工作。但 Agent 随之分散到各平台存在，不再有集中入口，这对其"始终只有一个 Agent"的用户感知构成挑战。

**上下文边界与 A2A（8.3）。** 组织配备 Super-agent 时，实际上是在划分上下文共享与隔离的边界；跨边界的协同即 Agent 间通信（A2A）。在互不共享底层上下文、各自代表不同权限边界的前提下，如何安全可靠地协作，仍属开放问题。

**安全与隐私（8.4）。** 这是四个问题中最硬、最易被架构图掩盖的一个。文章提出一个方向：让 Agent 在完全不接触凭据的情况下使用凭据。这背后是一整套设计（凭据注入、代理调用、作用域收窄），但文章仅点到为止。

# 结论

文章的贡献可归纳为三点：

1. **把 Session 降级为实现细节。** 用户面对的是一个 Agent，而非 N 个会话。
2. **把 Fast/Slow Path 贯穿全系统。** 过滤、路由、上下文组装、投机执行，均采用"确定性代码 + 模型兜底"的分工。
3. **把执行环境留在原地。** 循环上云，环境原地待命，使系统能够接入带未提交修改与私有凭据的真实工作流。

文章未提出新理论，其全部设计是将计算机系统的经典思想（分层、缓存、局部性、投机执行、存算分离、控制回路）迁移至 Agent 系统。其价值恰在于此：当一个领域开始系统性复用另一领域的成熟模式时，通常意味着它正从"技巧"走向"工程"。

一个不在文章开放问题列表之内、但值得继续追问的问题是：

> 若人的注意力是瓶颈，则"减少人的介入"与"让人更好地监督"是两条不同的路径。Super-agent 选择了前者（自动分派、静默修复、仅在需要决策时打扰）；但当任务复杂度上升、出错代价增大时，前者将面临后者的问题——如何确认结果可信。

存算分离（第 8 节）与 Watchdog（第 8.3 节）只回答了这一问题的一半。
