# 1 什么是 LLM Agent

大语言模型（LLM）的单次调用是**无状态的**：输入一段文本，输出一段文本，过程结束，不产生任何副作用，也不保留任何记忆。

Agent 是在此之上增加三层能力后得到的系统：

1. **工具**——模型不再只能生成文本，还可以调用外部函数或程序（搜索、执行代码、读写文件）。
2. **控制循环**——模型在多轮"思考—动作—观察"中推进任务，而非一次性回答。
3. **状态**——模型需要跨轮维护上下文，记住已经做过什么、正在做什么。

由此，LLM Agent 可以概括为：**LLM + 工具 + 控制循环 + 状态**。前两者决定它能做什么，后两者决定它如何持续地做。

# 2 ReAct：Agent 的控制循环

**ReAct**（Yao et al., 2022）给出的范式至今仍是最通用的 Agent 控制循环。它把一次任务推进拆为三个交替出现的步骤：

- **Think（思考）**：基于当前上下文，判断下一步该做什么。
- **Act（动作）**：调用一个工具或给出最终回答。
- **Observe（观察）**：获取工具返回的结果。

关键机制在于第三步：**观察结果会回灌进上下文**，成为下一轮"思考"的输入。于是上下文在循环中不断增长，形成一份"已发生事件"的日志。这一机制的含义是：Agent 的"记忆"并非外部数据库，而是这条不断增长的上下文轨迹——这也是后续所有上下文管理问题（第 4 节）的来源。

一个例子：让 Agent 查文档并修复一个函数。

1. Think：需要先找到该函数的定义位置。
2. Act：调用检索工具，查询符号表。
3. Observe：工具返回文件路径与行号。
4. Think：读取该文件，定位问题。
5. Act：调用编辑工具，修改代码。
6. Observe：返回 diff。

# 3 工具调用

工具调用（function calling / tool use）是 Agent 与普通 LLM 的核心差别之一。其工作方式为：

- 开发者声明每个工具的**名称、描述与参数 schema**；
- 模型在推理时决定是否调用、调用哪个工具、传入哪些参数；
- 运行时执行该函数，把结果作为一条新消息回灌进上下文。

两个与架构相关的细节值得注意：

**其一，工具描述的质量直接影响调用质量。** 模型依据描述判断工具是否适用，描述含糊的工具体现为"看不到"或"乱调用"。

**其二，调用有同步与异步之分。** 同步调用会阻塞整个循环直到工具返回；异步调用则立即返回一个"已启动"的句柄，结果稍后作为事件回灌。这一区分是理解《Super-agent 架构精读》中 `start()` / `stop()` 设计的前置。

# 4 上下文窗口与 token 预算

上下文窗口（context window）是模型单次能"看到"的 token 上限。它由三部分组成：

- **系统提示**：角色设定与规则，长期占用；
- **对话历史**：包括每一轮思考、动作与观察，随循环增长；
- **工具输出**：检索结果、文件内容、执行日志，可能非常长。

窗口是**稀缺资源**，原因有二：其一，超出上限的部分会被截断或遗忘；其二，即便在窗口之内，过长上下文也会稀释模型的注意力，使关键信息被淹没。

因此，上下文管理的基本问题不是"装下更多"，而是"在正确的时刻装入正确的少量"。

# 5 Session 与多会话

Session 是承载一段连续交互的上下文容器。一个 Session 大致对应一份从头累积的上下文轨迹。

单会话架构存在三类固有限制：

- **串行**：一个循环正在等待工具返回时，无法处理新的输入；
- **混杂**：多个任务的中间细节堆叠在同一窗口，相互污染；
- **不可恢复**：Session 状态只存在于该进程内，进程终止即丢失。

这三类限制引出一个更一般的问题：当需要同时推进多个任务、且任务之间需要彼此隔离时，系统的状态该如何组织？这是多会话与多智能体要解决的问题。

# 6 为什么需要多智能体

单个会话内的 Agent 存在两类固有限制：其一，循环串行，吞吐受单次推理速度约束；其二，多个任务的上下文混杂在同一窗口，相互干扰。

多智能体的核心思路是把任务拆给多个**执行单元**，让它们并行、隔离地工作。但拆分引入了一个新问题：**由谁决定"这件事交给谁"，以及各单元之间如何共享必要的信息。** 这正是"编排"要解决的内容。

# 7 三种编排范式

## 7.1 orchestrator-worker（中心编排）

一个主单元（orchestrator）负责规划与分派，多个工作单元（worker）在隔离的上下文中执行子任务，只回传结论。

- **优点**：结构清晰，主单元掌握全局。
- **代价**：主单元成为信息与吞吐的瓶颈——所有分派与汇总都经过它；若子任务同步执行，整个系统可能阻塞在等待某个子任务上。

## 7.2 subagent（临时委派）

主 Agent 在执行过程中，把某个子问题交给一个**临时**的 subagent，后者在干净的窗口中深挖，只回传一小段结论（通常 1–2k token）。

- **优点**：主 Agent 的窗口不被子任务的中间过程污染。
- **要点**：subagent 通常"只读"——回答问题、返回结论，不直接修改主 Agent 的工作状态，以避免上下文不共享带来的冲突。

## 7.3 事件驱动与 pub/sub（对等协作）

不设中心编排，各单元通过**事件**通信。核心是发布/订阅（pub/sub）：

- **Topic**：事件的分类（或"话题 + 来源"的组合）；
- **Subscription**：单元声明自己订阅哪些 Topic；
- **投递**：事件发布后，路由给所有订阅者。

事件驱动适合"单元不知道谁将处理消息"的场景——投递关系由订阅声明决定，而非逐个硬编码。

# 8 三个协议，管三件不同的事

Agent 系统涉及三类交互：与工具、与其他 Agent、与人类。三个协议分别对应一条边界。

**MCP（Agent 与工具之间）。** **Model Context Protocol**（Anthropic，2024）解决 Agent 与工具/数据之间的集成问题。此前每个工具都需要定制的连接器（N 个工具 × M 个 Agent）；MCP 让工具以 server 的形式暴露能力，Agent 以 client 的形式接入。MCP 属**纵向集成**：它连接的是"一个 Agent 和它的资源"。

**A2A（Agent 与 Agent 之间）。** **Agent2Agent**（Google 发起，现归 Linux Foundation）解决多个独立 Agent 之间的协作。每个 Agent 通过一张 **Agent Card** 声明能力与鉴权方式，协作方以 `SendMessage` 发起任务，通过状态机与事件流跟踪进度。其关键原则是 **Opaque Execution**：不暴露内部记忆与工具——因此 A2A 适合实例之间、权限边界清晰的对等协作。

**AG-UI（Agent 与人之间）。** **AG-UI**（Agent-User Interaction Protocol）解决 Agent 与前端界面的对接。它以事件流描述 Agent 的全部进展（Run 生命周期、文本消息、工具调用、状态增量、子 Agent 事件），前端据此做增量渲染，而不必等 Agent 全部完成再一次性输出。

三者并不冲突，而是分属三条边界：MCP 管纵向集成，A2A 管横向协作，AG-UI 管前端交互。一个完整的 Agent 系统通常三者并用。

# 9 持久化执行

普通 Agent 的运行状态存在于进程内：进程一旦崩溃、重启或迁移，未保存的上下文即丢失。对于长时间运行、需要跨设备或跨会话持续存在的 Agent，这是不可接受的。

**持久化执行（durable execution）**要解决的问题是：让执行状态能够跨越进程的生命周期存活——崩溃后可以恢复，迁移后可以继续。其核心在于**把状态从执行过程中外置**。

# 10 状态放在哪：三条路线

持久化执行的关键设计决策是"状态放在哪、如何恢复"。三条主流路线对应三种取舍。

**事件重放。** 把每次执行记录为一条事件，形成事件历史。崩溃后，代码从头重放事件历史以重建状态。代价是代码必须确定性——给定相同的事件历史，必须做出相同决策。

**检查点。** 以固定粒度保存状态的快照（checkpoint）。崩溃后回滚到最近的检查点。代价是恢复精度取决于检查点粒度。

**有状态对象。** 把状态绑定到一个有身份的对象上（如 Durable Object），对象在哪状态就在哪；对象被驱逐后靠落盘数据恢复。代价是状态与特定运行时绑定，迁移受限。

三条路线可统一为一条标准：**崩溃之后，系统需要重算多少东西。** 事件重放靠重算，检查点靠回滚，有状态对象靠续命。

# 11 计算、状态与执行环境的分离

持久化执行的另一个维度，是把 Agent 系统拆成三部分并各自解耦：

- **计算**：推进 Agent 循环的逻辑，可以做成无状态、可水平扩缩的容器；
- **状态**：会话日志等需要持久化的数据，存入数据库；
- **执行环境**：代码仓库、工具链、凭据等，往往绑定在具体设备上。

分两层的意义在于：第一层（计算与状态分离）使 Agent 摆脱单机生命周期，云端持久在线；第二层（计算与执行环境分离）使执行环境不必跟随计算上云——真实环境中的未提交修改、私有凭据、内网依赖难以复制，应留在原地，仅以轻量 daemon 按需接入。

# 12 如何评测一个 Agent 系统

评测 Agent 系统常用的指标有两类：

- **成功率**：任务完成的占比。多步任务通常以"环境状态是否被改造成应然状态"判定，而非只看最终回答。
- **完成时间**：从任务下发到结果交付的耗时，常以 p50 / p95 分位描述——p95 反映"慢的那一部分"。

一个容易被忽略的指标差异是 **pass@k 与 pass^k**：

- **pass@k**：k 次运行中**至少一次**成功的概率，衡量"能否做出来"；
- **pass^k**：k 次运行**全部**成功的概率，衡量"是否每次都可靠"。

对于每天运行数百次、持续在线的系统，决定用户体验的是 pass^k 而非 pass@1——单次成功率会显著高估可靠性。
